# 楽曲・アルバムの重複排除（デドゥプリケーション）仕様

現在、Spotify等からのインポート時における「同名異曲」や「同一楽曲の別バージョン」の取り扱い方針について、現状の課題と今後の仕様方針を定義します。

## 1. 現状のインポート仕様（なぜ別々の曲として登録されるのか）

現在の `credit_fetcher.py` のインポート処理は、**「SpotifyのTrack ID」のみをキーとして楽曲の同一性を判定**しています。

Spotifyの仕様上、同じ楽曲であっても以下のように収録先が異なると「**全く別のTrack ID**」が割り当てられます。
* 例: 「シングル盤の曲A」と「アルバム盤の曲A」と「ベスト盤の曲A」はすべてIDが異なります。

現状のDB設計ではこれをそのまま別の `Song` として登録してしまうため、同じタイトルの曲がデータベース上に複数登録されてしまう（別曲扱いになる）状態になっています。

## 2. 今後の統合方針（提案）

この問題に対処し、ユーザーの直感に合った「同じ曲は1つの曲（ハブ）としてまとめる」ための統合ルールを提案します。

### A. ISRC（国際標準レコーディングコード）による完全一致統合
Spotifyから取得できるメタデータには、世界共通の音源識別コードである `ISRC` が含まれています。
* **方針**: 新規楽曲インポート時、すでに同じISRCを持つ楽曲がDB（またはSongAlias等の別テーブル）に存在する場合は、新規の `Song` を作成せず、既存の `Song` のIDを使用します。
* **メリット**: リマスター盤などでない限り、確実に同じ音源を紐付けることができます。

### B. タイトルとメインアーティスト名による（仮）統合
ISRCが異なる場合（再録バージョン、Liveバージョン、別言語版など）でも、「楽曲（MusicalWork）としては同じ」であるケースがあります。
* **方針**: インポート時に `ISRC` が違っても `(曲名, メインアーティスト)` が完全一致する場合は、別々の `Song` として登録しつつも、同じ `MusicalWork`（作品・楽曲の概念）配下に自動的に紐付けるようにします。
* **メリット**: 楽曲詳細画面で「Other Versions」として自動的に関連バージョンが表示されるようになり、データが散らばるのを防げます。

### C. UI上での「マスター楽曲」と「派生トラック」の扱い
アルバム詳細画面（AlbumTrack）からは、Spotify上の本来のTrack IDが必要になる場合があります（再生ウィジェット用など）。
* そのため、`Song` 本体は1つに統合しつつも、`AlbumTrack` テーブル側に `spotify_track_id` を持たせるか、統合された別IDのリストを保持するテーブルを用意するなどのDBスキーマ改修が必要になります。

## 3. 次のアクション（レビュー依頼）

上記のような「ISRCでの自動統合」と「同名曲のWork自動紐付け」のロジックをインポートスクリプト（`credit_fetcher.py`）に組み込む改修を行ってもよろしいでしょうか？
方針に問題がなければ、DBスキーマの軽微な修正（AlbumTrackへのSpotify ID追加等）と併せて実装を進めます。
